# Benchmark frame sampling

AdminApp's retained-refresh assertion targets the existing revision label, waits for its exact updated text, and then checks visibility. A missing future-text locator caused Playwright 1.63 to build a full-body accessibility snapshot on each pending assertion attempt. Protocol and renderer tracing identified those diagnostic calls as the dominant refresh measurement overhead. The stable label avoids that unrelated traversal while retaining the same real refresh, exact revision/sample value, visibility, owner/focus/draft assertions, and CPU/frame boundaries. No refresh baseline or limit changes.

AdminApp, date, and Composer use `bench/frame-sampling.ts`. The browser installs the frame loop and PerformanceObserver synchronously and acknowledges installation directly. The controller does not poll readiness with `waitForFunction`, whose default animation-frame polling added a variable frame of harness delay to these short operations.

The frame measurement boundaries remain unchanged: sampler installation through the operation, its correctness/retention checks, three settling frames, and the legacy sampler's final animation-frame drain. Five fresh-context runs, deterministic calibration workloads, the 10% regression allowance, three-consecutive-increase drift detection, frame limits, Long Task limits, and layout/identity checks are unchanged. Chart and table work-time gates retain their own browser-local boundaries. Benchmarks are reference-workload regression checks, not isolated component latency or user-facing guarantees.

AdminApp, date, and Composer drain three rendering frames after fixture readiness, CPU calibration, and retained-node capture, before installing their first interaction sampler. Preparation never opens the picker, so the measured date opening remains cold. This separates setup rendering from interaction work without adding retries, changing frame clocks, or weakening gates. Date field/trigger/input identity and the committed value are checked atomically against captured native DOM references in one browser evaluation; the instant and time-zone checks follow the same ownership pattern. Native keyboard navigation uses the selected-cell focus established by opening the popup rather than making a benchmark-only refocus call. Production coverage verifies that initial focus. Correctness checks and native keyboard events remain in the measured window. All three artifacts include each raw run and its frame intervals, rather than only pooled summaries.

Composer checks its editor, same-origin iframe/document, app, query builder, draft, table, and query owners in one browser evaluation instead of six to eight separate controller lookups. Theme/viewport trigger searches are scoped to the configuration bar instead of computing accessible names across the complete component palette. Native pointer clicks are unchanged. The phone workload checks the computed 390px width in the same evaluation and still permits the table to leave the DOM while requiring the surviving shell, iframe, builder, and draft; the restored desktop table is captured before measuring query edits. This preserves the existing responsive contract and strengthens actual node-identity checks without remounting the preview or changing what the workload does.

AdminApp uses the same atomic ownership approach in `bench/admin-app-owners.ts`. Original native shell, content, chart, details, and draft references survive presentation changes; copied marker attributes cannot pass a replaced-owner check. Configuration searches stay within the configuration panel and open select layers. Palette visibility, dialog role, and accessible name are checked on the palette itself instead of computing ARIA roles across the heavy page. Native clicks, keyboard events, viewport changes, and all correctness checks remain within the unchanged CPU/frame window. This removes measured query-engine allocations rather than filtering GC or discarding slow samples. Production coverage exercises real heavy chrome actions and rejects a cloned content node with identical marker attributes.

Allocation profiling also identified accidental theme compilation during ordinary accent-data imports. Accent data and token derivation now live separately from bundled theme construction, preserving all root exports while allowing the compiler, palette audit, and primitive generation to be tree-shaken. Isolated copied-package consumer checks enforce that boundary. Palette audits convert each color once per simulation instead of once per pair; all reference distances, ordering, and validation gates remain exact. The client facet hot loop avoids a per-row array iterator without changing row-major accessor order, counts, or error handling. TimeSeries resolves source columns once and copies the selected samples column-wise rather than allocating an iterator at every output point; bucket endpoints, extrema, hidden-series contributions, gaps, and timestamp alignment remain exact. Heap sampling and timeline tracing are separate diagnostics, never enabled during regression qualification; qualification never forces GC.

Where supported, the sampler also records [Long Animation Frames](https://w3c.github.io/long-animation-frames/) as diagnostics, including blocking time and rendering/style-layout offsets relative to sampler installation. These can distinguish script/rendering work from a delayed frame even when the Long Tasks list is empty; they do not replace either existing gate. A negative start offset identifies an animation frame that began before the sample. The hosted date failure at `9c53f21` recorded one 283.4ms frame and zero Long Tasks; its summary-only artifact does not establish the source of that delay. The preparation fix and richer diagnostics still need hosted qualification.

## CPU regression metric

Long Animation Frame diagnostics also retain individual script timings, invoker/type, source URL/function/character position, forced style/layout time, pause time, and window attribution. Long Tasks retain their start offsets and names in `longTaskTimings`, alongside the unchanged `longTasks` duration array used by gates. All offsets share the sampler installation origin. Unsupported fields are null; browser-withheld source names/URLs can be empty. These are passive observer records, not an enabled profiler, and script durations are wall time rather than thread CPU. Missing script attribution does not prove the browser was idle. Existing artifacts remain interpretable without these additive fields.

Hosted comparison [35261753598](https://github.com/gemologic/sheen/actions/runs/35261753598) passed every CPU gate. Search CPU improved in every pair (median paired change -27.3%), as did retained refresh (-9.3%). Pair 1 recorded a 50.1ms theme frame in both versions. Pair 4 candidate search run 5 recorded a 101ms Long Task and an 83.4ms frame, while the entire interaction consumed only 45.198ms of renderer thread CPU. That discrepancy warrants attribution, not a claim that search executed 101ms of JavaScript. The old artifact cannot distinguish off-CPU scheduling/waits from other browser causes. Keep the failed samples and all current limits; inspect the added attribution on the next hosted failure before choosing an application fix or proposing a runner policy change.

For paired measurements on fresh GitHub runners, use the manual [AdminApp comparison workflow](./benchmark-comparison.md). It preserves existing gates and compares both application commits with a shared diagnostic harness.

Local `--repeat-each` runs preserve later artifacts as `*-benchmark.repeat-N.json` rather than overwriting the first run's canonical artifact. CI's single run keeps its existing filename. This preserves failing raw runs even when a later repeat passes.

AdminApp, date, and Composer use `bench/cpu-sampling.ts`: a dedicated Chromium CDP session enables `Performance` with `timeDomain: "threadTicks"`, then measures the increase in `TaskDuration` around the entire frame-measurement callback. CPU reads bracket observer installation, the native operation, correctness/retention checks, settling, and the final observer drain. Calibration uses the same counter around its deterministic callback. Fixtures, including Composer's preview app and table, must be ready and drain three rendering frames before calibration so initial rendering does not inflate its denominator. The normalized gate is the median of five **interaction task-CPU / calibration task-CPU** ratios, not elapsed time divided by a CPU loop. Missing, invalid, non-increasing counters and overlapping samples fail closed. Each session is detached before its context closes.

[CDP's thread-running-time domain](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Performance.pdl) avoids charging idle frame/controller/network waits as active renderer task CPU. Renderer work performed during those waits still counts. Main-thread JavaScript, layout, and other renderer tasks are included; this is not whole-browser, server, GPU, or worker CPU. Real production browser tests verify idle waits remain mostly uncharged and CPU work in Composer's same-origin preview contributes to the parent clock. Cross-origin out-of-process previews are not covered by this measurement contract.

Artifacts identify `measurement: "cdp-task-duration-thread-ticks-v1"`, include per-operation `taskMs` and per-run `calibrationTaskMs`, and retain `frames.durationMs`, `calibrationsMs`, and `rawMedianMs` as **elapsed diagnostics only**. Each raw run records host load averages at its start and end as contention diagnostics, never as a reason to discard failures. Date and Composer use schema/baseline v2; AdminApp uses v3. CPU histories start with new five-run production captures, explicitly attributed to the local machine. Old elapsed ratios are not compared to or mixed with CPU ratios. The target CI remains pinned Ubuntu 24.04 and Playwright 1.63.0; calibration is intended to normalize runner speed, not prove equivalence across hardware. First hosted CPU qualification and future browser/runner changes need artifact review. CPU measurement excludes off-CPU waiting but cannot remove contention's effects on caches, memory bandwidth, CPU frequency, or the unchanged frame/Long Task gates. Qualification should use an otherwise idle machine.

To deliberately capture a candidate baseline locally, run a profile with `SHEEN_CAPTURE_CPU_BASELINE=true`, for example `SHEEN_CAPTURE_CPU_BASELINE=true SHEEN_DATE_BENCHMARK=true SHEEN_BENCHMARK_PORT=4356 pnpm exec playwright test --config bench/playwright.config.ts` against a fresh production build. Capture mode bypasses only CPU baseline comparison, retains every frame/Long Task/layout/identity/footprint gate, and labels the artifact `qualification: "baseline-capture"`. It is forbidden in CI. Review the complete artifact and commit its five-run normalized medians into the versioned history, then rerun normally with capture unset. Capture success is not regression qualification, and baselines must not be inflated to absorb failures.

Stopping collects pending observer entries before disconnecting and removes the active marker. Production browser tests exercise a real delayed refresh, overlapping-start rejection, disposal/reuse, and an actual 80ms blocking task. The blocking-task test follows the same three-settling-frame boundary as the benchmarks before stopping. Per the [HTML rendering model](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering), animation-frame timestamps describe rendering opportunities, not callback execution time; a queued frame can retain a timestamp from before the blocking task finished. Stopping immediately after the task could therefore collect the Long Task while missing its delayed frame interval. The test still requires both a Long Task and a frame above 50ms, and includes all collected timings in assertion failures. No sampler clocks, benchmark boundaries, or thresholds change.

The positive blocking fixture runs its 80ms workload in a native rendering callback registered after the sampler's callback. A timer task can report an 80ms Long Task while queued animation-frame timestamps produce an interval exactly at 50ms, which does not exercise the strict **greater-than-50ms** frame gate. Blocking the recorded rendering opportunity gives a reliable stimulus for both independent gates without changing the workload duration, sampler, settling boundary, or assertions.

AdminApp waits for the revision in its status bar rather than repeatedly searching the complete heavy page. Correctness and retained-owner checks remain inside the measured window. Chart formatting and SVG geometry depend on an equality-checked locale, not the complete theme state, so color-only changes redraw styled surfaces without constructing new Intl formatters or rebuilding localized models. The token bridge reads each requested CSS property once per scope redraw rather than once per chart subscription. Production tests count real native Intl constructions and token reads, verify all twenty theme-workload canvas owners survive, and check that locale changes still update canvas/SVG data tables and formatter hooks.

ThemeProvider and ThemeScope likewise pass equality-checked locale and direction values into the UI backend's i18n context. Direct getters over the complete theme state had caused existing floating layers to recreate their positioning subscriptions on color-only changes, forcing style/layout work during theme selection. Independent [Solid memos](https://docs.solidjs.com/reference/basic-reactivity/create-memo) suppress those unrelated updates without freezing real locale or direction changes. Production coverage on `/theme-reactivity` observes native scroll-listener registration while exercising retained root and scoped popovers, drafts, localization, RTL, and selection. Theme attributes and token redraws remain reactive; SSR, hydration ownership, and all benchmark gates are unchanged.
