# Benchmark frame sampling

AdminApp, date, and Composer use `bench/frame-sampling.ts`. The browser installs the frame loop and PerformanceObserver synchronously and acknowledges installation directly. The controller does not poll readiness with `waitForFunction`, whose default animation-frame polling added a variable frame of harness delay to these short operations.

The measurement boundaries remain unchanged: sampler installation through the operation, its correctness/retention checks, three settling frames, and the legacy sampler's final animation-frame drain. CPU calibration, five fresh-context runs, normalized baselines, regression allowances, frame limits, long-task limits, and layout/identity checks are unchanged. These timings include controller overhead and are regression diagnostics, not isolated component latency or user-facing guarantees. Chart and table work-time gates retain their own browser-local boundaries.

Stopping collects pending observer entries before disconnecting and removes the active marker. Production browser tests exercise a real delayed refresh, overlapping-start rejection, disposal/reuse, and an actual 80ms blocking task. The blocking-task test follows the same three-settling-frame boundary as the benchmarks before stopping. Per the [HTML rendering model](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering), animation-frame timestamps describe rendering opportunities, not callback execution time; a queued frame can retain a timestamp from before the blocking task finished. Stopping immediately after the task could therefore collect the Long Task while missing its delayed frame interval. The test still requires both a Long Task and a frame above 50ms, and includes all collected timings in assertion failures. No sampler clocks, benchmark boundaries, or thresholds change.

AdminApp waits for the revision in its status bar rather than repeatedly searching the complete heavy page. Correctness and retained-owner checks remain inside the measured window. Chart formatting and SVG geometry depend on an equality-checked locale, not the complete theme state, so color-only changes redraw styled surfaces without constructing new Intl formatters or rebuilding localized models. The token bridge reads each requested CSS property once per scope redraw rather than once per chart subscription. Production tests count real native Intl constructions and token reads, verify all twenty theme-workload canvas owners survive, and check that locale changes still update canvas/SVG data tables and formatter hooks.

ThemeProvider and ThemeScope likewise pass equality-checked locale and direction values into the UI backend's i18n context. Direct getters over the complete theme state had caused existing floating layers to recreate their positioning subscriptions on color-only changes, forcing style/layout work during theme selection. Independent [Solid memos](https://docs.solidjs.com/reference/basic-reactivity/create-memo) suppress those unrelated updates without freezing real locale or direction changes. Production coverage on `/theme-reactivity` observes native scroll-listener registration while exercising retained root and scoped popovers, drafts, localization, RTL, and selection. Theme attributes and token redraws remain reactive; SSR, hydration ownership, and all benchmark gates are unchanged.
