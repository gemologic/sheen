# Table URL state and saved views

`createTableUrlState(router, parameter, schema)` uses the same structural location/navigate adapter as AppShell without importing a router runtime. `read()` returns absent, accepted, or invalid; duplicate parameters and malformed or schema-incompatible state fail closed. `write()` validates and version-serializes the whole table state, defaults to replace navigation with scroll retention, and preserves unrelated query parameters plus the hash. `clear()` removes only its parameter. Both return unchanged without navigating when the canonical target already matches. Apps choose whether a deliberate view change should push history.

The URL is state, not authorization. Never place row data, credentials, callbacks, or selection payloads in it. `URLSearchParams` owns encoding. The serializer's 262144-code-unit ceiling is a parser safety limit, not a claim that browsers, proxies, analytics systems, or servers accept URLs that large; applications with large state should use a saved-view ID instead.

`createSavedViews(adapter, schema)` owns asynchronous list/save/delete publication while the app owns per-user persistence and authorization. There is no localStorage fallback. Save serializes a validated table state before calling the adapter. Returned records are copied and checked, updates retain list position, and restore deserializes against the current schema before exposing a state candidate. An incompatible old view remains visible and deletable but returns `invalid` when restored, allowing a user-facing reset or migration instead of silently dropping fields.

Each operation receives an AbortSignal and monotonic ownership token. Starting a newer operation aborts its predecessor; ignored-abort completions cannot publish. Failure retains the accepted list and captures the exact operation for retry. Clear immediately drops local records and invalidates pending work; it cannot undo an already accepted external side effect. The table still owns whether applying a restored state triggers a successful data request, and must retain its current accepted rows if that request fails.

Five real loopback-HTTP tests cover list/save/update/delete, versioned restore, retained-list failure/retry, incompatible stored state, ignored-abort supersession, clear, and disposal. Loupe uses its actual Solid router for eight Chromium executions covering semantic query/hash preservation, replace/push history, back traversal, delayed hydration without navigation, and duplicate/malformed rejection. A separate real HTTP saved-view fixture passes six Chromium executions for deterministic hydration without implicit persistence, CRUD/restore, and failure recovery. DataTablePage composes the same adapter into one compact switcher with save and management dialogs; renaming preserves the stored table-state snapshot, destructive deletion requires confirmation, and failed operations retain accepted table content with exact retry.
