# Pane restoration implementation boundary

AppShell registers its primary ScrollArea as `main`. Additional panes call `usePaneScrollRestoration(id, viewportAccessor)` under the shell, using unique nonempty IDs and the actual scrolling element. ScrollArea's ref supplies that viewport. Duplicate IDs fail explicitly. Keep the shell mounted across routes; its position cache belongs to that owner and is released with it.

Positions are keyed by the adapter's optional entryKey plus pathname, search, hash, and pane ID. Adapters without an entryKey have URL-only restoration and cannot distinguish duplicate URL entries. Solid Router's adapter attaches a random `__sheen_entry_key` field to native history-state records, preserving the enumerable application fields that the pinned router itself retains. This field is reserved for Sheen; applications must not author it. It is browser history metadata, not a token or user identifier. The owning browser entry retains its key across back/forward, replacement, and adapter remounts. Push navigation assigns a fresh key even when application state copies an older entry's metadata.

Mounted Solid adapters share a reference-counted bridge over that document's `history.pushState` and `history.replaceState`. It delegates each write exactly once and restores the previous methods when its final owner disposes, without overwriting later third-party hooks. If a later hook retains a disposed bridge, it delegates without adding metadata. Keep Solid Router as the sole router owning this document. Push writes include the pinned router's `_depth` bookkeeping, incremented from the current logical entry rather than bounded `history.length`; replace writes preserve that depth. This avoids a second router write per push and preserves native traversal blocking after browser history fills. Initial or previously untagged record entries need one metadata adoption write. Entry identity is independent of `_depth`, and no separate entry map is retained.

The adapter publishes settled URL coordinates and entry identity atomically. The pane-position cache remains bounded independently. Browser coverage traverses more than 50 visits, preserves duplicate-URL offsets, blocks dirty traversal, replaces forward history, copies application state, shares and remounts adapter owners, restores native methods on final disposal, and retains server viewports during hydration. Entries created before this bridge owned history can still carry the pinned router's preexisting ambiguous depth values; adopting their keys does not reconstruct that missing traversal bookkeeping.

Panes also capture their final settled offsets when their location owner cleans up, before the next location initiates restoration. This preserves scroll changes whose native scroll event has not fired yet, including traversal of older entries lacking reliable before-navigation notification. Pending restoration and inactive viewports remain excluded from saving.

Each shell retains at most 256 pane/location pairs, evicting the least recently read or written pair. This bounds record count even with dynamic pane IDs. Evicted locations behave as unvisited, without affecting app data. Positions are immutable finite-coordinate snapshots, retaining fractional and negative RTL offsets. Five cache unit cases cover the default cap, eviction/recency, dynamic IDs, collision-safe pair keys, and invalid inputs.

First mount with no saved entry preserves existing native scroll without scheduling a reset during hydration. Later unvisited locations start at zero; revisited locations restore recorded offsets. Same-location content refresh does not initiate restoration. Restoration cannot record a location left before the shell's mount hooks run. The lifecycle fixture observes its requested refresh before navigating; separate delayed-hydration coverage retains early scroll. All seven browser cases pass three repeated runs after cache integration.

Restoration is scheduled in an animation frame. Content is ready by default. For asynchronous route content, set AppShell's `contentReady={false}` before initiating navigation and keep it false while the current route's content is incomplete. Custom panes pass `{ ready: () => boolean }` as the third argument to usePaneScrollRestoration. The app owns that readiness state, including error outcomes and superseded requests; sheen does not infer completion from an idle timer.

While incomplete, restoration observes size and waits for unreachable offsets. When ready, it settles at the current clamped boundary, records that position, and disconnects its size observer. Later unrelated growth cannot revive the old target. Wheel, pointer, or scrolling-key input also stops pending restoration and size observation. Event listeners, ResizeObserver, and scheduled frames clean up on location change, viewport change, or disposal.

A zero offset alone does not prove a new visit's restoration has settled: the previous visit can already be at zero while the new frame remains pending. User-scroll tests use native wheel input and assert each intermediate history destination and entry identity. Tests that assign scroll offsets programmatically wait through the restoration frame first. Application code that intentionally scrolls during pending restoration must coordinate its content readiness and scroll ownership instead of expecting an imperative offset to cancel the scheduled target.

Four Chromium cases pass three consecutive runs each: independent main/sidebar offsets across browser back/forward, unchanged offsets on refresh, retained viewport identity through delayed hydration, restoration after a real delayed response grows the content, and cancellation of that pending restoration by a real pointer interaction. The interruption assertion runs after two animation frames following content growth. Repeated navigation initially exposed stale cached sidebar offsets because scroll events can arrive after a history attempt. Panes now also capture their actual offsets through the adapter's before-navigation subscription, without preventing navigation. Three AppShell SSR cases pass, including slot access to dirty-state and pane contexts. The provider boundary now precedes slot resolution; previously sidebar slots could not use shell contexts.

The expanded suite passes seven Chromium cases. Native wheel and PageDown input cancel pending restoration before delayed row growth. Removing a sidebar while restoration is pending, completing the real request, and remounting it reuses its pane ID without a duplicate-registration error, restores its saved offset, and continues navigating correctly. This tests disposal/remount behavior, not a heap or comprehensive listener-leak audit.

The fixture now includes a two-axis sidebar in a runtime-switchable direction scope. Eight restoration browser cases pass. The extended RTL case passes three repeated runs: negative horizontal and positive vertical offsets restore independently across back/forward, then recover after a real delayed response expands both previously clamped dimensions. This qualifies native Chromium RTL offsets, not transformed coordinate systems or cross-browser behavior.

Nine Chromium cases pass two repeated runs after adding readiness. A real delayed response returning permanently short content settles at zero; expansion afterward and revisiting the route do not revive the previous 700px target. Existing delayed-growth, interruption, hydration, remount, and RTL cases continue passing.

Ten restoration cases plus three navigation-guard cases pass in Chromium. A repeated-URL regression distinguishes 700px and 200px visits to the same URL and verifies a new entry replacing forward history starts at zero. That case and permanent-shrink history revisit pass three repeated runs each. Delayed-load fixtures traverse back to their original entry rather than pushing a new copy of the URL.

Eleven restoration cases plus three navigation-guard cases pass in Chromium. The full-shell disposal case removes the shell while a real response and restoration are pending, lets the response finish, and mounts a new shell. The replacement viewport starts at zero rather than inheriting the old 700px target, then independently records and restores a new 200px position. No page errors occur. This establishes observable owner isolation and continued navigation, not garbage collection or comprehensive listener-leak proof.

Below 768px, AppShell registers the document's scrolling element instead of its main pane. Document listeners capture scroll and interruption events, and pending restoration observes body growth. Phone/document and desktop/pane coordinates use distinct cache keys. The active-container check reads the current media match when saving: CSS can clamp a former viewport before the media-query change callback runs, and that clamped zero must not overwrite its saved position. A router-enabled shell owns manual browser history restoration until disposal; do not enable a competing router document-restoration implementation.

Twenty combined Chromium shell, restoration, and navigation cases pass after this integration. Three phone cases cover back/forward offsets with real wheel input, delayed hydration retaining early document scroll and server DOM, and desktop/phone round trips retaining independent 700px/200px positions. Programmatic test scrolling immediately after navigation could race the scheduled restoration; the interaction case uses real wheel input, which also exercises pending-restoration interruption.

Eight phone cases pass three repeated Chromium runs (24 executions). Real delayed responses restore the document to 700px when rows grow; completed short results settle at zero and later expansion does not revive the old target. Real wheel input and a native touchscreen tap independently cancel pending restoration before growth. The short-result case waits through two frames before expanding, so the expansion click cannot conceal an unsettled restoration. Disposal returns history.scrollRestoration to auto when that was the prior setting and preserves a preexisting manual setting across remount/disposal. Lint and root/Loupe typechecks pass.

Touch-swipe/momentum behavior, mobile drawer integration, and cross-browser behavior still need qualification. Touch-tap coverage is not a physical-device or gesture-scroll claim. No session-storage or cross-shell persistence is promised.
