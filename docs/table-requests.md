# Server table request ownership

createTableRequests accepts an app callback taking state and AbortSignal and returning rows/total plus any app-typed response metadata. State includes explicit pagination and must be structured-cloneable. This framework-neutral controller exposes request, retry, getSnapshot, clear, and dispose. It does not fetch automatically or supply a reactive UI subscription; the DataTable adapter must publish snapshots around awaited requests.

An optional second argument, { state, result }, supplies initial accepted results for SSR/hydration. Construction clones the query, validates pagination/completeness, and adopts the result without calling transport. Empty totals normalize to page zero. A nonempty dataset whose initial requested page needs clamping throws rather than publishing an invalid page or performing hidden I/O. The app must supply equivalent initial state/data on server and client and retain responsibility for safe serialization and authorization. Result row identity is preserved.

Each request aborts its predecessor and carries a monotonically increasing bigint token. Late success and error completions cannot publish over a newer request, even if transport ignores abort. Accepted state and result are published together. Pending requests and failures retain the previous accepted object; requested state remains distinct for previous-result labeling and retry. Caller state and transport input are separately cloned. Treat exposed snapshots and accepted results as read-only.

Responses pass through pagination validation. A deletion-invalidated page can trigger a clamped refetch without publishing its empty response. Four total attempts bound moving-total churn; exhaustion retains accepted data and reports an error for explicit retry. Empty totals settle at zero without another request. Continuous mode never walks pages and rejects incomplete results.

clear invalidates the current request, aborts transport, and immediately drops accepted/requested/error state. The app must call it on authorization/account boundaries before showing data for a different principal. dispose additionally rejects future work. A retry with no requested state returns failed without making a request; applications should offer retry only for a failed request.

Clear publishes empty state before firing abort listeners and rejects synchronous request restarts during that operation, including nested clear calls. Normal supersession may trigger a newer request from an abort listener; token checks ensure the outer superseded request does not replace its controller. This does not authorize future requests: apps must still stop old-account producers and enforce authorization in their transport. Work explicitly submitted after clear returns is treated as new work.

Proof: seven real loopback-HTTP tests cover delayed and rejected responses, ignored abort, stale-error suppression, retained accepted rows, retry, clear/disposal, synchronous abort-listener reentrancy, clamped refetching, empty results, bounded moving totals, and truncated continuous results. With the eight pagination tests, fifteen tests pass. The clear-restart test reproduced an incorrect accepted response before the atomic-clear fix. Table build, lint/typechecks, and existing isolated consumer checks pass. Manifest validation was last checked at 77 components / 80 examples; these changes add no component. No transport mocks or new dependencies were added.

The Loupe table-requests fixture imports the built table package and publishes controller snapshots around awaited operations. It starts from deterministic initial accepted rows rendered on the server, without an on-mount refetch. Its stateless HTTP endpoint supplies stable IDs, changing revisions, delayed/error responses, and a deliberately non-cancellable slow request. Rows are keyed by ID so accepted revisions update cell text without replacing local input drafts.

Four Chromium cases pass twice each. The refresh case samples animation frames for retained row count, editor identity, focus, and text selection while a revision arrives. Different-query requests visibly label previous rows and disable their actions, including native programmatic click. Late-result and clear tests wait for controller completion counters, not merely finished network responses. Cleared rows remain empty after an ignored-abort response completes. The delayed-JS hydration case retains server row/editor DOM, pre-hydration draft text, focus, and selection, with no duplicate data request or browser exception. Two additional constructor tests bring the table suite to seventeen passing tests. Isolated package consumers verify initial state adoption and disposal. Lint/typechecks, table build, and Loupe's production client/server build pass; the browser tests ran against its development server.

The public DataTable now renders this lifecycle with retained virtualized rows, previous-result state, error/retry, atomic page acceptance, and authoritative initial results that do not refetch during hydration. The earlier three-row controller fixture remains useful for ignored-abort, clear/dispose, editor, focus, and selection ownership cases. Editing conflicts, dynamic SSR-loader serialization, and the remaining table features stay separate.
