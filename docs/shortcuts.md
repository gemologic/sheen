# Shortcut implementation boundary

`createShortcutRegistry({ platform, development, warn?, onError?, onPending?, onChange? })` is the registry core. It owns sequence timers but does not install document listeners or detect operating systems, edit controls, or active scopes. The browser owner must supply those facts consistently after hydration.

Register `{ keys, scope, label, group, run }` and retain the returned idempotent disposer. Scope IDs are application/owner identities, not global mutable state. Dispatch receives a normalized input record plus scope IDs ordered outermost to innermost. A modal owner must omit suspended outer scopes, rather than expecting an absent modal binding to block fallback automatically.

`mod` resolves to Meta on macOS and Control elsewhere. Same-scope aliases collide. Development rejects a duplicate with both labels; production warns and uses the newest registration, restoring the older one when the newer registration is removed. Snapshots are frozen data-only records and expose shadowed registrations for future tooling. Registry disposal clears bindings and rejects new registrations.

Control/Meta R, L, T, and W bindings are reserved, including modified forms and later sequence strokes. Unmodified/Alt-only shortcuts are suppressed in editing contexts. Composition cancels pending input; repeated keydown events are ignored without extending the timer. Shift-generated punctuation uses its actual key value, so `?` matches a keyboard event carrying Shift. Dispatch accepts an optional beforeRun callback for recognized actions or sequence prefixes, allowing native default prevention even if an action throws.

Ten unit cases cover alias collisions, platform resolution, production replacement/removal, scope precedence, input suppression, browser protection, prevention-before-failure, sequences, real timer expiry, and disposal. They invoke real registry operations on data records, not fake browser events. These are not DOM, hydration, keyboard-layout, assistive-technology, or dialog-integration evidence.

ShortcutProvider owns a document keydown listener and registry; useShortcut registers reactively in that context and cleans up with its Solid owner. Supply stable development configuration and optionally an explicit platform override, plus reactive activeScopes (default global). Use exactly one provider per document; nested providers are rejected. The listener respects defaultPrevented, detects editing through the composed event path, suppresses AltGraph/composition/repeat, and prevents matched keys before invoking actions. Synchronous failures and live async rejections go to onError or are rethrown in a microtask. Async callbacks return Promise<void>; incidental synchronous values returned through void callbacks are ignored. Rejections arriving after registration/provider disposal are consumed without notifying replacement owners; disposal does not cancel application transport or undo actions.

The native Chromium fixture verifies pane precedence, real input typing, modified shortcuts inside inputs, failure reporting without losing input focus, binding disposal, provider disposal, and clean remount without duplicate invocation. Six unit/SSR cases additionally verify server rendering without browser-global access, missing-owner diagnostics, registry policy, and prevention-before-failure ordering. This does not prove every editing widget, platform layout, dialog integration, or browser shortcut compatibility.

Four Chromium cases pass, including real delayed 409 responses while live, after binding removal/remount, and after provider removal/remount. The fixture consumes the response body before rejecting so request-completion assertions observe the actual transport boundary. Live errors report once, stale failures do not notify replacement owners, and subsequent shortcuts work without page errors.

Seven Chromium cases now pass twice (14 executions). Delayed script loading preserves an early editor draft, focused server node, and a queued scope change; subsequent shortcuts fire once. Handled native key events do not reach the action, while contenteditable prose suppresses single-key bindings but permits modified actions. A real delayed successful request changes a reactive binding from mod+j to mod+h: the old action remains available while pending, then is removed, and the new action fires once without replacing the focused editor or its backward text selection. This fixture uses a getter in useShortcut's definition so Solid can track the changed key.

## Sequences

Separate strokes with whitespace, for example `g i` or `mod+k ctrl+i p`. Each accepted prefix starts a fresh one-second timer; a monotonic deadline also rejects expired completions if the timer callback has not run yet. The innermost scope with a matching first stroke owns the entire sequence. Sibling branches are allowed. A complete binding that is also another binding's prefix is rejected in both development and production, naming both labels; it cannot simultaneously execute immediately and wait for more keys. Exact sequence duplicates retain the normal development/production policy.

Escape cancels pending input and is unavailable as an unmodified continuation stroke. An unmatched continuation cancels the sequence and is considered as a fresh shortcut. Modifier presses do not interrupt a pending sequence. Scope changes, composition, editing, reserved browser keys, candidate removal, new registrations, and registry disposal clear pending state. The provider also cancels on handled keys, AltGraph, focus changes, pointer input, and window blur, and removes all listeners with its owner.

`usePendingShortcut()` returns a Solid accessor of frozen `{ keys, displayKeys, label, scope, completed }` candidates. Render localized feedback in an existing status region without moving focus. `ShortcutPending` and `ShortcutSheet` now supply the reusable feedback/help UI described below; shell-wide placement remains unfinished. Core consumers can use `onPending` and `cancelPending()` directly.

Ten Chromium cases pass twice (20 executions), including native completion, visible pending choices, real expiry, focus/Escape cancellation, and binding/provider removal and remount. Eleven unit/SSR checks pass. Automatic scope/platform handling, cross-browser and keyboard-layout qualification, tooltip association, shell pending/help UI, and baseline bindings remain open.

Character-only sequences are also covered by [WCAG 2.1.4](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html). Input suppression alone does not satisfy it. Sheen uses the criterion's turn-off path: a visible app-owned preference disables every all-character sequence as well as single-character bindings, while the generated help remains reachable by its native button. Focus-scoped component typeahead is independently exempt under the criterion.

## Character-shortcut preference

`ShortcutProvider characterShortcuts={enabled()}` now accepts a reactive user preference, defaulting to true. The app owns its setting, persistence, and localized control. Wire an existing Switch's `checked` and `onCheckedChange` to the same signal. Do not hide this control behind a character-only shortcut. Resolve stored preferences before enabling bindings, using deterministic SSR state and the existing hydration handoff; the provider itself does not access storage.

With the preference false, character-only bindings are excluded from dispatch without unregistering them. Classification covers the entire sequence: Shift does not make letters or punctuation non-character shortcuts, while Ctrl/Meta/Alt or a non-character key anywhere in the sequence makes it eligible. A modified first stroke followed by a bare character remains usable. Snapshots expose `characterOnly` for future settings/help rendering. Preference changes clear pending state; re-enabling never revives an old prefix. Core consumers supply the same optional `characterShortcuts` flag in each dispatch input.

Thirteen unit/SSR tests and twelve Chromium cases (24 executions across two repeats) pass. The native setting test moves focus out of the Switch before checking disabled bindings, separately verifies modifier actions/sequences, and re-enables question-mark handling. A delayed-hydration test changes the native switch before JavaScript, retains its node/focus/state through hydration, and confirms that the first shortcut dispatch respects the disabled setting. The fixture control is keyboard-operated, not a forced click through the decorative switch track.

This meets the W3C's documented G217 turn-off technique and avoids the F99 failure: the control is visible and keyboard operable, the setting takes effect for native key events, and all-character sequences are classified as character shortcuts. The app owns persistence so it can resolve the preference through the same deterministic SSR/hydration path as its other settings. Loupe proves a preference changed before hydration is retained, and the generated help annotates disabled entries while its native trigger stays usable. No particular speech-recognition product was run; that remains a cross-platform compatibility boundary, not a missing WCAG 2.1.4 mechanism.

## Generated shortcut sheet

`useShortcutBindings()` exposes immutable live inventory records. Core consumers receive these through `onChange` after registration, removal, and disposal, or call `snapshot()` directly. Records include stable registration IDs, group/scope labels, platform-formatted `displayKeys`, character classification, and same-scope shadowing. They never contain action callbacks. A failed registration leaves the accepted inventory intact. Formatting currently uses Ctrl/Meta on other platforms and macOS symbols for explicitly configured macOS bindings; platform detection remains separate unfinished work.

`ShortcutSheet` renders that inventory in the existing scoped Dialog, grouped by `group`, with Kbd labels, explicit scopes, and localized disabled/replaced annotations. Unchanged registration rows retain their DOM across inventory changes. It accepts Dialog's title, trigger, controlled state, focus, footer, and styling props, but generates its own body. The list explains that scopes may be inactive; it is not a promise that every displayed binding currently executes.

The application owns opening. Loupe's fixture registers `?` to open it, retains a visible native trigger when character shortcuts are disabled, and restores the actual question-mark origin on close. Dialog now suspends outer scopes automatically, as described below. The sheet itself does not install another document listener or silently register a competing `?` binding. Shell-wide wiring remains unfinished.

Integration exposed two defects. Kobalte 0.13.13's modal close callback ignored defaultPrevented and forcibly focused its trigger after sheen's explicit returnFocus succeeded. The existing core patch now respects cancellation in both the JSX and compiled-JS dialog entry points. Consumer scaffolds/migrations must carry the patch or qualify an upstream fix; npm dependents do not inherit this workspace's pnpm patches automatically.

Seventeen targeted unit/SSR tests, 23 Chromium cases covering shortcuts/sheet/dialogs/navigation guards, existing dialog visual baselines, lint/typechecks, and 71-component/72-example metadata validation pass. The sheet has three native cases: question-mark opening/grouping/trap/suspension/return focus with no ownership warnings, delayed live rebinding with retained unrelated labels, and visible help plus disabled annotations when character shortcuts are off. Dedicated sheet delayed hydration, visual/RTL/contrast matrices, large inventories, automatic shell integration, and full accessibility qualification remain open.

Its optional `label` overrides the scoped `pendingShortcut` message; native attributes and merged classes pass through. Mount it once in an existing status/toolbar slot, not conditionally after receiving a prefix. The reserved control-small block size stays unchanged when idle, pending, completed, or cancelled. The parent must constrain inline size; long candidate lists are visually ellipsized while their full text remains in the DOM. It never takes focus or animates layout.

## Automatic platform selection

Omit `platform` to resolve keyboard conventions once on mount. Before then, no provisional registry is created and the inventory is empty, matching server output. Child useShortcut effects wait for that registry without replacing their DOM. Explicit `mac` or `other` remains a stable construction-time override, useful when the application already has authoritative configuration. Development policy is also read once. The native listeners resolve the current registry through an accessor and remain owned by the provider.

The resolver maps Mac-prefixed hints and iPhone/iPad/iPod to macOS-style modifiers; missing/unknown hints fall back to Control. `navigator.platform` is used only for keyboard conventions, not capability detection, matching [MDN's documented modifier-key use case](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/platform#determining_the_modifier_key_for_the_users_platform). No browser globals are read during SSR. Do not mistake platform hints for physical keyboard-layout detection or a guarantee against browser privacy overrides.

Seventeen targeted unit/SSR tests, 20 Chromium automatic/explicit shortcut and sheet cases, UI build, lint/typechecks, and 72-component/73-example validation pass. The automatic fixture uses the actual host browser hint, never a mocked navigator. Both immediate and delayed hydration retain an early draft/focus/node, show one formatted binding, fire once, and work once after provider removal/remount without page or ownership errors. Pure resolver tests cover Apple, Windows, Linux, and absent/unknown inputs; this is not native macOS/iOS/Windows browser qualification.

The fixture exposed an existing async-dispatch bug: a callback typed void may still return a signal setter's numeric value at runtime. Calling `.catch` on any truthy return crashed after successful actions. Registry adoption now uses Promise.resolve, ignoring incidental synchronous values while retaining live rejection reporting and stale-owner suppression. A focused unit regression and the real setter fixture cover this boundary. Automatic focus/modal scope selection and shell integration remain unfinished.

## Automatic modal scopes

Dialog, AlertDialog, ConfirmDialog, and ShortcutSheet now acquire a modal scope while their accepted open state is true, provided they are inside ShortcutProvider. The default scope ID is unique and stable for that dialog owner. Pass `shortcutScope` to register modal-specific actions under a known ID; that ID must be nonempty and distinct from background/application scopes. Simultaneously active dialogs cannot share an explicit scope ID. Dialogs outside ShortcutProvider continue to work without a keyboard provider.

The newest active modal replaces the entire base activeScopes list. Nested dialogs therefore suspend both the application and enclosing-dialog actions. Closing or disposing a dialog removes its exact activation record, restoring the next modal or the latest application base scopes. Scope changes cancel pending sequences. Base pane/view scope selection is still application-owned, and non-sheen overlays are not automatically integrated.

The shortcut-sheet fixture now relies on this integration instead of rewriting activeScopes when help opens. Three native modal cases prove nested scope precedence and Escape restoration, cancellation of an earlier global sequence, open-inner-owner removal/remount, and imperative confirmation suspension of an enclosing dialog. The removal test deliberately focuses a surviving outer control before dispatch; it does not claim automatic focus recovery when both an inner modal and its trigger are removed.

Thirty Chromium modal/shortcut/sheet/dialog/navigation-guard cases, five targeted SSR cases, UI build, lint/typechecks, and 72-component/73-example validation pass. Metadata validation caught ConfirmDialog inheriting the new prop; its forwarding and metadata are included. An older help test was querying hidden background content while the modal was open and now checks the accepted action after closing. Automatic focus-based pane/view scopes, shell integration, duplicate-ID error presentation, and cross-browser qualification remain open.

## Focus-based view and pane scopes

`ShortcutScope scope="inspector"` adds a native div boundary with no default role, tab stop, or layout styling. Match that ID in useShortcut registrations. Its native attributes, children, ref callback, and merged classes are retained. Scope IDs must be nonempty, non-global, and unique among simultaneously mounted focus scopes. Reactive ID changes release the prior registration; disposal releases the exact element and cancels pending input.

For a keyboard event, ShortcutProvider derives registered boundaries from the actual composed event path, outermost to innermost, and appends them after base activeScopes with deduplication. A focused inner pane therefore shadows its view and global scope; focus outside every boundary uses only the base scopes. Debug data attributes are not used as authority. Registration uses provider-owned element records, not document-wide attribute selectors. A modal overrides this entire focus/base list while open.

The DOM path is intentional: portalled content does not inherit the originating pane's focus scope. Sheen modals use their separate modal scope; other portalled widgets need explicit integration. Nested pane scopes inside a modal do not override its modal scope. This component does not infer scope from pointer hover, retain a previously focused pane after focus leaves it, or add a focus stop to otherwise noninteractive content.

Twenty-six native Chromium focus/modal/automatic/explicit shortcut and sheet cases pass, plus the new SSR test, UI build, lint/typechecks, and 73-component/74-example validation. Three focus-specific cases cover global/view/left/right precedence, native Tab into an editor with single-key suppression and modified pane actions, cancellation when focus moves between panes, removal/remount of a scope ID, modal suspension/restoration, and a retained early-focused server draft hydrating into the left scope. Shell integration, portalled nonmodal-widget ownership, duplicate-ID error presentation, and broader keyboard/cross-browser qualification remain open.

## Menu keyboard ownership

DropdownMenu and each submenu register their open content element with the optional enclosing ShortcutProvider. Events whose composed path includes that owned element bypass the registry unless Control or Meta is pressed. This leaves menu typeahead, navigation, and Escape with the widget without preventing the event or stopping its propagation. Acquisition and disposal cancel pending shortcut sequences. Closed content does not retain ownership, and menus outside a ShortcutProvider remain independent.

This is explicit element ownership, not a selector that guesses behavior from ARIA roles. Portals still do not inherit their originating pane's scope: eligible modified shortcuts use the base or active modal scope, while closing restores the trigger's normal pane scope.

The original regression focused Gamma with `g` while also firing the global action. It now retains menu typeahead without the background action, permits Control+J, restores pane shortcuts after close, and survives reopening. A nested-menu case proves separate submenu ownership and one-layer Escape restoration. Thirty-six menu/shortcut Chromium cases passed before adding that nested case; the final five-case pane suite also passes. Seventeen targeted unit/SSR tests, UI build, lint/typechecks, and 73-component/74-example validation pass. ### Bound control actions

Button, Tooltip, and IconButton accept a typed `ShortcutAction` containing keys, optional scope, label, group, and optional development policy. The nearest ShortcutProvider registers that action with native `click()` as its execution path, so form semantics and the component's existing handler remain authoritative. Disabled or loading controls keep their binding discoverable but cannot activate through pointer, native keyboard, programmatic click, or shortcut dispatch. Outside a provider the same component remains an ordinary native control without a document listener.

Tooltip distinguishes typed actions from display-only strings. A typed action displays the registry's platform-formatted chord after hydration; a string remains literal and does not register. IconButton inherits this behavior. This avoids separate binding and hint records drifting apart. `useShortcut` remains the API for actions with no single native control owner, and duplicating the same action through both paths is a collision by design.

### Development theme cycling

ShortcutDefinition accepts `developmentOnly: true`. A registry constructed with `development: false` ignores that registration entirely: no dispatch, inventory entry, collision, pending cancellation, or browser-event prevention. Its disposer is harmless. This is application policy, not authorization or a guarantee that debug code is stripped from bundles. Supply the correct construction-time development flag from the app build configuration.

With shortcutHelp enabled, AppShell registers `mod+shift+d` using this flag. It cycles the preference dark → light → system → dark through `theme.setMode`, preserving the theme provider's validation and persistence/error path. System is a preference, not a third resolved color scheme. The action returns the persistence promise to the registry so live failures reach the app's onError handler. Dialog modal ownership suspends the global action while help is open, just like other global bindings.

Nineteen registry/shell unit and SSR tests pass. Seven native shell cases pass, including explicit production-policy absence, development cycling through all three preferences from a focused input, retained editor identity/value/focus, help inventory, and the existing shell hydration/layout checks. This does not prove optimized-production dead-code elimination, native macOS shortcuts, or cookie-persistence failures through this specific binding.

### Sidebar toggle

When sidebar content is present, the shell renders localized responsive Toggle sidebar controls with aria-controls/aria-expanded. These require ThemeProvider but not ShortcutProvider. Enabling shortcutHelp also registers global `mod+/`; the tooltip hint comes from the shared registry's platform-formatted binding. Removing sidebar content disposes the controls and registration. The shortcut operates on the current layout's independent accepted state.

`defaultSidebarOpen` initializes local visibility, defaulting to true. `sidebarOpen` supplies controlled accepted state; `onSidebarOpenChange` receives proposals, with no implicit persistence. Rejected proposals do not hide the sidebar or move focus. An accepted close moves focus from inside the sidebar to its toggle, or the main scrolling region when no toggle exists. Focus already elsewhere stays there. Hiding applies hidden/inert to the existing aside rather than unmounting it, preserving drafts, node identity, and scroll for reopening.
