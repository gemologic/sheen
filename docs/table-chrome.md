# DataTable chrome and refresh states

DataTable headers, footers, row actions, bulk actions, and regional states are one presentation of accepted table state. They do not own application data operations. Column headers publish sort and layout intents through the existing table state contracts. A footer callback receives the complete accepted transformed client view, even when the visible table is paginated. In server mode it receives only the accepted response rows, so full-query totals and aggregates must come from authoritative server metadata rather than a footer reduction over one page.

`variant="framed"` is a self-contained surface for standalone embedding. `variant="integrated"` removes the outer border and radius, fills its application pane, and joins table-owned toolbar, header, viewport, footer, and pagination chrome. Omitting `variant` defaults to framed except under `DataTablePage`, which supplies integrated presentation context. An explicit variant always wins. Both variants use the same state, rows, controls, and responsive markup.

DataTable renders exactly one named capability toolbar. Explicitly configured search and active FilterBar chips occupy its leading query region; the accepted localized result count, all-matching selection, available export formats, retained export download, and column controls derive from the same accepted table owner. Unavailable capabilities do not leave inert placeholders. At narrow component widths, a CSS container query replaces all secondary action controls with one More actions menu whose submenus reuse the same export and column item models. This is deterministic in server CSS, so hydration neither measures nor rearranges the initial toolbar. Search/filter/result owners and accepted rows remain mounted while its component container crosses the overflow boundary.

`DataTablePage` continues to own only page title, breadcrumb, tabs, saved-view adapter chrome, page actions, and regional states. Its page-action toolbar has a distinct accessible name and cannot configure table search, filters, columns, export, counts, or selection. DataTable does not accept page actions. This keeps two legitimate layers from rendering a second copy of either control family.

Density is inherited from the effective theme scope rather than copied into table state. Compact density uses the 28px row token and scales header/footer cells, editors, selection controls, toolbar controls, pagination, and mobile-card spacing from the same density tokens. Changing density must retain those owners and remeasure the virtualizer; it must not select another implementation.

Sortable headers keep the button's accessible name limited to the column label and publish state through a separate description. The primary key alone receives `aria-sort`, as required by the ARIA table pattern. Every sorted header also exposes a visible direction arrow and numbered priority badge plus `data-sort-direction` and `data-sort-priority`, so secondary order remains perceivable without overloading `aria-sort`. Resize separators report their current width in pixels and support pointer, arrow-key, and double-click auto-fit paths. Reorder grips are quiet at rest, visible on hover and keyboard focus, and retain the menu-based move path. A pinned region ends in a control-border rule and shadow; its cells inherit the active row fill so scrolling never exposes a mismatched slab.

Virtualization and pagination preserve logical table coordinates rather than exposing only the current DOM window. A flat table reports its full accepted row count, including the header and optional footer; every rendered row reports the corresponding one-based `aria-rowindex`, including the global page offset. Treegrids report `aria-rowcount="-1"` because grouping, collapsed hierarchy, and delegated children can make the eventual expanded total unknown, while their currently rendered rows remain monotonically indexed. The table reports every declared column in `aria-colcount`, including the selection column. Every rendered header, body, state, and footer cell reports `aria-colindex`, so hiding a column leaves an explicit logical gap instead of renumbering the surviving cells. Selectable data rows expose `aria-selected` in both native table and treegrid presentation; their native labeled checkboxes remain the direct selection controls.

These rules follow the W3C APG [grid and table properties](https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/) contract: using a total row count requires indices on every rendered row, and noncontiguous rendered columns require both a full column count and cell indices. The native table role remains intact for flat data. Grouping and hierarchy alone opt into treegrid behavior.

Rows use distinct opaque fills for rest, hover, keyboard focus, selection, selected interaction, and retained previous-query content. Sticky selection and pinned cells consume the row's shared fill variable rather than painting over it. Previous-query tinting survives a request failure until that exact requested query is accepted or superseded, and pagination, sorting, filters, selection actions, and replacement context menus stay guarded for that entire interval.

Supply one `actions` array for both row context menus and the bottom selection action bar. Each callback receives an immutable selection payload, the selected rows currently loaded in the accepted view, and an optional anchor row when invoked from a context menu. Right-clicking an unselected row first makes that row the explicit selection. Right-clicking an already selected row preserves the wider selection. `Shift+F10` and the platform Context Menu key expose the same menu, while the visible selection bar keeps every action reachable without right-click. During a delegated request or unaccepted search draft, replacement menus and selection actions are disabled so they cannot operate on retained rows under a requested query.

The selection bar overlays the table instead of changing viewport geometry. It uses a raised, opaque themed surface, bounds wide action sets with horizontal overflow, and keeps the localized tabular selection count separated from its actions. It mounts for its fast enter animation, becomes inert and accessibility-hidden immediately on close, and unmounts on the real animation-end event with a short reduced-motion fallback. Reduced-motion tokens reduce both animations to zero. Clearing selection returns the table to its ordinary row navigation without changing accepted data.

Zero rows have four distinct meanings:

- Cold load has no accepted result. It reserves the final table geometry immediately, shows no loading treatment under 200 ms, then reveals inert skeleton rows.
- Empty means the accepted unfiltered dataset has no rows.
- No results means an accepted search or filter has no matches. Its content-sized fallback row remains fully visible above a sticky footer, offers Clear filters or the more accurate Clear search and filters label, and restores focus to the table viewport after the unfiltered state is accepted.
- Initial error has no accepted result and renders an alert with retry in the table body. A refresh error retains the accepted table and renders an actionable banner above it.

Revalidation never replaces accepted rows with skeletons or blank markup. The table keeps row DOM, focus, selection, scroll, and editing drafts intact. Under 500 ms it shows no progress UI. At 500 ms a thin progress line and the explicit “Refreshing, showing existing results” status appear. Query-changing controls and row operations remain guarded until the requested state and its rows are accepted atomically. A failure leaves the accepted result fully opaque, visibly labeled Previous results, and retryable without pretending the requested query was accepted.

The opt-in phone card presentation follows the same timing and acceptance rules. It is documented separately in [Phone DataTable cards](table-mobile.md), including deterministic server markup and bounded continuous paging.

Server-rendered tables should receive an `initialResult` for the exact deterministic initial state. Hydration reuses the server table, rows, controls, and committed cell content and does not issue a duplicate mount request. Context menus are unavailable before JavaScript, so the platform menu remains untouched; after hydration the same retained row opens one scoped menu and Escape restores its focus. Cold-load timers, refresh timers, action handlers, and portaled content begin only after mount.

## Pagination practice

Pagination and data ownership are independent:

- Use continuous client mode for a complete, bounded dataset that benefits from scanning or in-page find. Virtualization limits DOM nodes, not bytes, parse time, transformations, or memory.
- Use client pagination when page landmarks, shareable page state, or deliberate review batches help even though all data is local.
- Prefer numbered server pagination for large, expensive, frequently changing, or authorization-sensitive remote results. Apply filtering and a deterministic total order on the server before slicing each page.
- Use continuous server mode only when one response is complete and explicitly bounded. `rows.length` must equal `total`; DataTable never crawls hidden pages.
- Treat cursor/infinite loading as a separate future contract, not as `pagination={false}`.

There is no honest universal row-count cutoff. Decide from serialized payload size, row width, browser transformation cost, freshness, interaction design, and backend cost. Stable row IDs are mandatory in every mode. Client export and client footers operate over the complete accepted transformed view, not the visible page. Server export and full-query aggregates remain app/server responsibilities.
